# ADR 0001：架构风格与核心技术选型

- **状态**：Accepted
- **日期**：2026-10-24
- **决策者**：单人开发者
- **相关文档**：`docs/prd.md`

## 背景

本项目是单人开发的 A 股中低频量化系统（日线至分钟线），目标是尽快跑通「回测 → 模拟盘 → 小资金实盘」的最小闭环（见 PRD 的 P0 验收标准）。

约束条件：

- **人力**：1 人，全栈自担，开发时间碎片化。
- **预算**：个人自费，不承担商业数据库授权与云上多实例成本。
- **性能**：A 股全市场日线约 5000 标的 × 10 年，量级在 GB 以下；分钟线为单标的按需加载。不存在高频吞吐与低延迟撮合的需求。
- **演进**：策略需要反复迭代，回测结果必须可复现、可对账。

以上约束下，架构的主要风险不是「性能不够」，而是「复杂度吃掉了闭环速度」——过早引入分布式组件会让单人项目在联调、部署、排障上消耗超过策略研究本身的精力。

## 决策

采用如下三项决策：

### 1. 模块化单体（Modular Monolith），而非微服务

单一进程内按领域划分为清晰模块：`data`（采集与落地）、`strategy`（信号生成）、`backtest`（回测引擎）、`broker`（交易网关，模拟/实盘同接口）、`risk`（风控）、`report`（对账与报表）。

- 模块间**只通过显式接口通信**，禁止跨模块直接访问对方内部数据结构。
- 模块内允许自由重构，模块边界变更需走新的 ADR。
- 部署形态为单个可执行程序 + 一个本地调度入口（回测与盘后任务），模块可按配置裁剪启用。

### 2. 数据层从 Parquet + DuckDB 起步，而非直接上 DolphinDB Pro

- **存储**：行情按「标的 + 频率」分区落 Parquet（列式、压缩、零运维、版本可追溯）。
- **计算**：DuckDB 直接对 Parquet 做 SQL 查询与聚合，服务研究阶段的探索与因子计算。
- **访问**：统一由 `data` 模块封装为仓储接口（如 `get_bars(symbol, freq, start, end)`），上层不感知底层引擎，为将来替换留出接缝。

### 3. 回测引擎采用事件驱动，而非纯向量化

- 引擎以「行情事件 → 策略回调 → 订单事件 → 撮合事件 → 账户更新」的时间轴推进，分钟线与日线共用同一事件循环，仅时间步长不同。
- 撮合层内置 A 股规则：T+1、涨跌停不可成交、停牌跳过、手续费与滑点模型。
- 策略层与实盘共用同一份信号代码；回测与实盘仅替换「行情源」与「交易网关」两个适配器。

## 后果

### 正面

- **闭环速度最快**：单进程、单机、零外部依赖，`git clone` 后即可运行回测。
- **一致性天然成立**：回测与实盘共用策略与撮合代码，避免「回测赚钱、实盘不认」的实现分叉——这正是 PRD 中「模拟盘信号与回测信号一致」验收项的技术前提。
- **可复现性强**：Parquet 文件 + 参数 + commit 即可完整复现一次回测；事件驱动天然记录逐笔事件流，便于对账。
- **迁移成本可控**：数据访问被仓储接口隔离，引擎被事件接口隔离，未来替换其中一层不影响另一层。

### 负面与代价

- **事件驱动比向量化慢一到两个数量级**：全市场分钟级多参数扫描会明显吃力，需要用「日线全市场粗筛 + 分钟级单标的精算」的两段式流程规避。
- **单进程无法横向扩展**：CPU 密集的参数寻优只能靠多进程并行，不能靠加机器。
- **模块边界靠自觉维护**：没有进程边界强制隔离，容易出现「图省事直接 import 对方内部函数」的腐化，需要靠目录规范与代码评审（哪怕只有自己）约束。
- **DuckDB 并发写能力弱**：不适合作为在线写入库，行情落地走「批量追加 Parquet + 元数据登记」而非实时写入。

### 放弃的选项

| 选项 | 放弃原因 |
| --- | --- |
| 微服务（K8s + 消息队列） | 单人维护成本远超收益，网络边界带来的排障难度会直接拖慢策略迭代；当前无多用户、无横向扩展需求。 |
| DolphinDB Pro | 授权成本高，且其核心优势（海量分钟/Tick 数据的高性能聚合、流计算）在本项目 GB 级数据量上用不满；运维复杂度对单人过重。 |
| 纯向量化回测（pandas/numpy 全矩阵运算） | 速度快但难以准确表达 T+1、涨跌停、停牌、资金约束等 A 股规则，且与实盘执行逻辑分叉，回测结论可信度低。 |
| 现成回测框架（Backtrader / vn.py 等） | 可快速起步，但撮合细节与交易网关受框架抽象约束，定制 A 股规则与自建对账链路时易被框架绑架；本项目核心资产正是引擎本身。 |

### 未来在什么条件下应重新考虑

1. **数据规模或查询模式变化**：单次回测加载数据耗时超过 5 分钟，或需要跨全市场分钟级历史做批量因子计算 → 重新评估 DolphinDB / ClickHouse / Arctic 等专用时序库，替换点位于 `data` 仓储接口之后。
2. **参数寻优成为瓶颈**：单机多进程跑完一轮全参数扫描超过数小时 → 先引入任务队列 + 多机 worker（仍保持单体），而不是直接拆微服务。
3. **出现第二个人协作或第二个策略团队**：模块边界需要独立发布与独立部署时 → 按当前模块边界拆分服务，此时边界已存在，拆分成本较低。
4. **策略频率下探到日内高频或需要实时风控**：事件驱动的单线程循环无法满足毫秒级响应 → 需要独立评估低延迟架构，可能推翻本 ADR 的决策 3。
5. **多人或多账户交易成为需求**：需要订单路由与账户隔离 → 交易网关需重新设计，但策略与回测层不受影响。
